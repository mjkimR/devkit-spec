# Common Completion and Knowledge Classification

Read this when approaching review or completion, and before any gate or Git action.

Every task MUST compare the final diff, requirements, relevant check results and Living Spec impact before reporting completion or integration. Correct an implementation defect in code; do not make documentation endorse it. Record authorized contract changes in capabilities/stories, structural changes in architecture, architecture decisions and lasting policy changes that override a MUST in ADRs (a one-off exception inside the approved scope is stated in the review or final report), and existing policy changes in rules/playbooks. New general rules and reusable procedures are optional promotions: draft first and request only decisions beyond existing authorization. No-impact changes need a reason, not a new document.

## Policy

Read `devkit spec policy` before deciding gate or Git actions:

- `[GATE_POLICY: dev-integration policy=ask]`: present the verified result and obtain the user's OK unless already authorized. The OK is not recorded (`ADR-integration-approval-asserted`): for a spec bundle, pass `--given dev-integration` to each `devkit workflow next --unit <dir>` after it, and name the OK as the authority in the integration report; a runner binds the gate to the PR ready state. An objection takes the stage's return path (`devkit workflow return --unit <dir> --to review-refine --note "..."`; an objection about direction is a close, see [classification](classification.md)). `policy=auto`: after review, reconciliation and required checks pass, report that the policy delegates the integration gate; `devkit workflow next` lists it as `[GATE_PASSED: dev-integration stage=integration-approval policy=auto source=policy]` (JSON `passed_gates`), the basis the integration report cites. Never describe policy delegation as a human review. Neither value grants commit, publication, merge or deletion authority; explicit user instructions and platform protections still apply.
- `GIT_POLICY` (worktree, pull request and branch cleanup): read [git policy](git-policy.md) and decide before the first edit.

## Reconciliation record

Formal specs use `specs/<YYYY-MM>/<YYYYMMDD>-<slug>/`. Create `reconcile.md` by PR preparation with `reconcile_id`, `status: pending|resolved`, and `targets` (`file`, `resolution: modified|waived`, and `rationale` for a waiver). `feature` and a target `action` are optional. Set resolved only after every target is reflected in the comparison diff or has a waiver of at least 20 non-whitespace Unicode characters. Required contract mismatches cannot be waived. Empty targets are allowed with no-impact reasoning in the body. Retain resolved records in place after integration; mark the spec completed. Keep deferred follow-ups traceable using the handoff below.

## Checks and commits

`git commit` runs the commit gate, which checks the index (`devkit rules check --staged` reproduces it); `devkit rules check --ci --base <ref>` checks merge-base through HEAD (default `origin/main`). These rules check the bundle's structure, IDs, task coverage, the agreement of spec, tasks and reconcile status, and the reconcile record's form (`RULE-reconcile-contract`: targets, resolutions, waiver length); in the commit gate and `--ci` they also require each `modified` target of a resolved record to be changed on the branch; they do not prove semantic impact. At commit time the staged diff counts together with the branch's earlier commits since its merge base with the branch it integrates into, so a target an earlier commit changed (the ADR the handoff promoted) is accepted without editing it again; `--ci` checks the same cumulative branch diff on the PR.

Intermediate commits pass the same commit gate; a `pending` reconcile record is allowed while the spec is not `completed`. An intermediate commit grants no merge authority and is never final completion evidence: the final cumulative check runs on the integrated head, and `dev-integration` still requires the Living Spec reflection and the resolved and completed states.

For formal specs, after `dev-integration` authorization the `integrate` stage (`spec-integrate`) integrates the base branch, re-verifies only what conflict resolution changed, confirms the reconcile record and runs the cumulative check; it does not restart code review and adds no approval gate. Delegated support roles return the fields in [envelope](envelope.md) and never change the index or HEAD.

The reconcile is verified at every effort and recorded as a `reconcile-check` envelope at `living-spec-draft` (the stage exit reads it): `low` the implementer's self-check, `medium` and `high` the separate reconcile-reviewer (medium may use the initial self-check exception in [effort](effort.md)); findings are fixed in the reconcile and a new `reconcile-check` written. At medium the implementer verifies fixes and decides further subagent calls; identify self-verification, its evidence and any initial omission reason in the check. Recheck impact after review fixes or changed verification inputs; return `reconcile.md` to pending when new targets are needed. Review final docs and governance changes too. Respect repository approval and required-check policy and existing merge authority. Never automatically delete a dirty worktree. Implementation complete, committed, integrated and session ended are distinct facts.

`session` depth (`sdd-session-*`) requires no Unit, envelope, gate record file, spec, plan, tasks or reconcile file, at every `activity-effort`. It still runs the checks and the effort's review and reports the change, effort, review result, verification and remaining constraints in the final response or PR body; a needed Living Spec change raises the depth to `spec`. Its commit is a plain `git commit` before `dev-integration` (the approval is given on committed work; a PR is pushed then), without `spec-integrate`, except on the base branch with no PR under `dev-integration = ask`: there start `dev-<slug>`, or get the approval before committing ([git policy](git-policy.md)). Use the user's authorized scope; do not silently abandon remaining work for the sake of a session time limit. PR and worktree choices follow [git policy](git-policy.md) in every lane. `/spec-feedback` optionally collects session observations; it neither replaces mandatory reconciliation nor terminates the user's session.

## Deferred Work Handoff

Before deleting a source proposal or reporting completion, inspect its roadmap and the final scope for concrete work explicitly retained for later. Each such follow-up MUST be tracked, by default as feedback for Backlog to review (`/spec-feedback`; Backlog turns it into a proposal when it needs one). A draft proposal is also allowed when the follow-up is concrete enough: then search existing proposals first (`devkit spec list proposal`, `devkit spec search "<topic>" --kind proposal`) and link or update a matching open `PROP-...`, otherwise create a `status: draft` bundle with `devkit spec proposal new <slug>`. Record the source spec/proposal, remaining scope, reason for deferral, dependencies or restart conditions, and expected acceptance checks. Group work with the same outcome; avoid duplicate proposals.

Reference the destination `FB-...` or `PROP-...` by its full ID from the source `reconcile.md` (or the final report of a `session` task), and reference back from a proposal to the retained source spec or Git history if the original proposal is removed. Capability documents describe current behavior; a future-work paragraph alone is not a handoff. Verify the destination exists (`devkit spec list feedback` or `devkit spec list proposal`) before claiming it is tracked. Drafting a follow-up does not accept it or authorize implementation.

This applies to concrete work being retained, not every speculative idea or explicitly rejected non-goal. Required acceptance criteria or defects still in the agreed scope MUST remain open; do not move them to a proposal merely to claim completion. Any scope change requires the existing agreement process. This handoff is part of completion in every route, not deferred until optional `/spec-feedback`.
