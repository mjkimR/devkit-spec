# Common Completion and Knowledge Classification

Read this when approaching review or completion, and before any gate or Git action.

Every route MUST compare the final diff, requirements, relevant check results and Living Spec impact before reporting completion or integration. Correct an implementation defect in code; do not make documentation endorse it. Record authorized contract changes in capabilities/stories, structural changes in architecture, architecture decisions and lasting policy changes that override a MUST in ADRs (a one-off exception inside the approved scope is stated in the review or final report), and existing policy changes in rules/playbooks. New general rules and reusable procedures are optional promotions: draft first and request only decisions beyond existing authorization. No-impact changes need a reason, not a new document.

## Policy

Read `devkit spec policy` before deciding gate or Git actions:

- `[GATE_POLICY: integration policy=ask]`: present the verified result and obtain the user's OK unless already authorized. The OK is not recorded (`ADR-integration-approval-asserted`): for a spec bundle, pass `--given integration` to each `devkit workflow next --unit <dir>` after it, and name the OK as the authority in the integration report; a runner binds the gate to the PR ready state. An objection takes the stage's return path (`devkit workflow return --unit <dir> --to review-refine|direction --note "..."`). `policy=auto`: after review, reconciliation and required checks pass, report that the policy delegates the integration gate; `devkit workflow next` shows it as `[GATE: integration policy=auto ... source=policy]`. Never describe policy delegation as a human review. Neither value grants commit, publication, merge or deletion authority; explicit user instructions and platform protections still apply.
- `GIT_POLICY` levels: `worktree=required` runs every Route 2, Route 3 and bugfix task in its own worktree from creation to cleanup ([worktree](worktree.md)); S-Lane is never required to. `worktree=auto` leaves it to you: a worktree when the task integrates through a PR, another task is in flight in this checkout, the user's uncommitted changes must stay put, the work is an isolated experiment, or the user asks; otherwise the current checkout. `pull_request=required` integrates every route, S-Lane included, through a PR (no `finish --merge`); `pull_request=auto` uses a PR when the task needs platform review or CI, the base refuses direct pushes, or the user asks, otherwise a local merge. A task integrating through a PR runs in a worktree. Report each `auto` choice and its reason in the final change report's assumptions. A request that names the checkout or the integration path overrides the policy for that task and is reported in the final change report's assumptions; otherwise an unavailable action the policy requires is a blocker, not silently downgraded. Decide these before the first edit, not after. Preserve the user's dirty checkout when creating isolation.
- `delete_branch=yes`: after a confirmed merge, and only under existing deletion authority, the merged task branch is removed with safe `git branch -d` after leaving it (`devkit worktree finish` does this for a worktree task). A dirty worktree, current branch, protected/base branch or unmerged branch prevents cleanup; report the remaining branch. `delete_branch=no` keeps it. This policy never deletes remote branches or forces deletion.

## Reconciliation record

Formal specs use `specs/<YYYY-MM>/<YYYYMMDD>-<slug>/`. Create `reconcile.md` by PR preparation with `reconcile_id`, `status: pending|resolved`, and `targets` (`file`, `resolution: modified|waived`, and `rationale` for a waiver). `feature` and a target `action` are optional. Set resolved only after every target is reflected in the comparison diff or has a waiver of at least 20 non-whitespace Unicode characters. Required contract mismatches cannot be waived. Empty targets are allowed with no-impact reasoning in the body. Retain resolved records in place after integration; mark the spec completed. Keep deferred follow-ups traceable using the handoff below.

## Checks and commits

`git commit` runs the commit gate, which checks the index (`devkit rules check --staged` reproduces it); `devkit rules check --ci --base <ref>` checks merge-base through HEAD (default `origin/main`). These rules check the bundle's structure, IDs, task coverage, the agreement of spec, tasks and reconcile status, and the reconcile record's form (`RULE-reconcile-contract`: targets, resolutions, waiver length); in the commit gate and `--ci` they also require each `modified` target of a resolved record in the diff; they do not prove semantic impact. Local staged evidence cannot substitute for cumulative PR evidence; a target already committed earlier in a feature is verified in the cumulative branch diff.

Intermediate commits pass the same commit gate; a `pending` reconcile record is allowed while the spec is not `completed`. An intermediate commit grants no merge authority and is never final completion evidence: the final cumulative check runs on the integrated head, and G3 still requires the Living Spec reflection and the resolved and completed states.

For formal specs, after G3 authorization the `integrate` stage (`spec-integrate`) integrates the base branch, re-verifies only what conflict resolution changed, confirms the reconcile record and runs the cumulative check; it does not restart code review and adds no approval gate. Delegated support roles return the fields in [envelope](envelope.md) and never change the index or HEAD.

Recheck impact after review fixes or changed verification inputs; return `reconcile.md` to pending when new targets are needed. Review final docs and governance changes too. Respect repository approval and required-check policy and existing merge authority. Never automatically delete a dirty worktree. Implementation complete, committed, integrated and session ended are distinct facts.

S-Lane requires no spec/plan/tasks/reconcile files. It still requires checks and a final Living Spec impact statement, even when the work ends without a commit; its commit after G3 authorization is a plain `git commit`, without `spec-integrate`. Use the user's authorized scope; do not silently abandon remaining work for the sake of a session time limit. PR and worktree choices follow the `GIT_POLICY` levels above in every lane. `/spec-feedback` optionally collects session observations; it neither replaces mandatory reconciliation nor terminates the user's session.

## Deferred Work Handoff

Before deleting a source proposal or reporting completion, inspect its roadmap and the final scope for concrete work explicitly retained for later. For each such follow-up, MUST search existing proposals (`devkit spec list proposal`, `devkit spec search "<topic>" --kind proposal`) and link or update a matching open `PROP-...`; otherwise create a `status: draft` bundle with `devkit spec proposal new <slug>`. Record the source spec/proposal, remaining scope, reason for deferral, dependencies or restart conditions, and expected acceptance checks. Group work with the same outcome; avoid duplicate proposals.

Reference the destination `PROP-...` by its full ID from the source `reconcile.md` (or the result report for S-Lane), and reference back from the proposal to the retained source spec or Git history if the original proposal is removed. Capability documents describe current behavior; a future-work paragraph alone is not a handoff. Verify the destination exists and appears in `devkit spec list proposal` before claiming it is tracked. Drafting a follow-up does not accept it or authorize implementation.

This applies to concrete work being retained, not every speculative idea or explicitly rejected non-goal. Required acceptance criteria or defects still in the agreed scope MUST remain open; do not move them to a proposal merely to claim completion. Any scope change requires the existing agreement process. This handoff is part of completion in every route, not deferred until optional `/spec-feedback`.
