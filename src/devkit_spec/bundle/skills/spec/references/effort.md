# activity-effort

How thoroughly one activity of a slug is done: `low`, `medium` (the default) or `high`, chosen when the activity starts and passed to its executor as run input, never stored in the Unit or the configuration. Backlog and inline Planning have no effort: Backlog's work is fixed and inline Planning is the intent agreement only.

**Always propose it.** When an activity starts, state the effort you propose and why, and let the user confirm it; never apply the default silently. A proposal's Planning effort is proposed in its `plan-intent` request ([classification](classification.md) §1). `medium` is the default proposal. Propose `high` when the work reverses an upstream or accepted decision (a strategy-layer rule, an ADR, an accepted proposal), creates a contract or a document kind, or affects more than one package (devkit, devkit-spec, autohub, or several packages of a monorepo); propose `low` only for work whose direction leaves nothing to criticize.

| Activity | `low` | `medium` | `high` |
| --- | --- | --- | --- |
| Planning (`proposal`) | questions only; no `scout` or `challenger` | one `challenger` pass always; `scout` when the direction needs evidence | two or more options compared, `challenger` required, re-review after changes |
| Development (`session`) | the author's self-review | one mandatory initial `code-reviewer` pass; the implementer verifies fixes and decides repeat calls | `code-reviewer` subagent review, re-review after the fixes |
| Development (Unit path) | the author's self-review and self-checked reconcile | one mandatory initial `code-reviewer` pass; a separate `reconcile-reviewer` check unless eligible for self-check below; repeat calls at the implementer's judgment | `code-reviewer` with re-review after fixes; a separate `reconcile-reviewer` verifies the reconcile independently |

Rules:

- **The floor stays.** Gates, the workflow's exit checks and `required` policies hold at every effort; effort sets only the optional procedure above them. On the Unit path the review envelope is recorded before `dev-integration` even at `low`; a `session` task reviews at every effort but records no envelope.
- **Review and evidence are separate.** `medium` and `high` always run the initial code review in a subagent, regardless of change size, for neutrality: a context other than the author's. A worker runs it nested (Host → worker → code-reviewer); a `session` task's Host or Cloud Agent runs it directly. The reviewer returns its fields as a message: on the Unit path the caller records them as the envelope, and a `low` self-review says so in its envelope; a `session` task reports the review method and result in its final response or PR body.
- **Reconcile is Unit-path only.** At every effort the implementer writes, fixes and resolves the Living Spec reflection and `reconcile.md`. The separate read-only `reconcile-reviewer` verifies it at `medium` and `high`, subject only to the medium exception below; a `session` task never calls that role. The implementer records every verification as a `reconcile-check` envelope at `living-spec-draft`, which exits only on the latest check with no open findings. Findings are fixed in the reconcile and checked again, never by reopening the code review.
- **Medium initial reconcile exception.** The implementer MAY omit the first `reconcile-reviewer` call only when all affected contracts and documents can be identified, their agreement with the actual diff can be directly demonstrated, and there is no unresolved contract interpretation or cross-component impact. A confirmed no-impact or a wording-only reflection preserving the contract can qualify; a small diff alone cannot. If any condition is uncertain, call the reviewer. When omitting the call, perform the self-check and record both the omission reason and the verification evidence in the existing `reconcile-check` envelope, explicitly identifying it as self-verification. This exception never skips the first medium code review, changes the effort, or bypasses a required policy; `high` always calls the reconcile reviewer.
- **Medium repeat calls are discretionary.** After the initial code or reconcile review, the implementer verifies fixes and subsequent changes against the findings, affected requirements, checks and docs impact. Further subagent calls are the implementer's decision, not automatic after each edit; expanded scope, uncertain correctness or contract interpretation are reasons to call again. Close findings with evidence in `reverify`, or write a new `reconcile-check` for reconciliation, identifying who verified the changed scope; do not imply the prior reviewer checked later changes. An initial failed or stale call never satisfies a required first review. This rule does not relax `high` re-review obligations.
- **Effort and integration policy are independent.** `dev-integration = auto` applies at `low` too, once the path's self-review, required checks and completion conditions hold; `low` adds no human approval.
- **Where it is recorded.** A worker writes the effort it applied in its `worker` envelope (`--effort`); a `session` task reports it in its final response or PR body. Model and reasoning settings are outside this axis.
