# Worktree procedure

Read this before work that runs in a task worktree: every `spec` and `proposal` activity in `direct` mode under `[GIT_POLICY: worktree=required ...]` (`[tool.spec] worktree`), and any task the `GIT_POLICY` levels in [git policy](git-policy.md) put in a worktree under `auto`, from the first step to the cleanup after merge. A request that names the checkout ("on main", "in the current branch", "in this worktree") overrides the policy for that task only; record the deviation as a user request, without its wording, in the final change report's assumptions.

Policy is read in the base checkout: a change to `[worktree]` or `[tool.spec]` governs the current task only once it is committed in the base, so make it there first (a `session` task). `devkit worktree` performs the deterministic steps; the session only changes directory. `<base>` is the checkout the request arrived in; `<branch>` is the activity branch, `plan-<slug>` or `dev-<slug>` ([branches](branches.md), which also covers a branch without a worktree and continuing an existing branch). The worktree is always `<parent of base>/<base name>-wt-<branch>` on `<branch>`, created from the base HEAD; the base working tree is never touched. A new worktree runs the `[worktree] setup` command (`GIT_POLICY setup=`) and `devkit sync`, so the managed files and the commit gate work there; a `WORKTREE_SETUP_FAILED` or `WORKTREE_SYNC_FAILED` warning names the `[FIX]` command to rerun before any work.

## 1. Start (in `<base>`, before any bundle or edit)

- `proposal` depth, Planning: `devkit worktree start plan-<slug>` and the printed `cd`; the proposal bundle is the unit.
- `proposal` depth, Development: the accepted proposal (`status: accepted` with `gate:plan-accept`, merged from its Planning branch) is in the base. Run `devkit worktree start dev-<slug>`, run the printed `[NEXT_CMD: cd <path>]`, then hand off **inside** the worktree as Development's first step: `devkit spec proposal handoff <slug>` (refused on another branch, `SPEC_PROPOSAL_WRONG_WORKTREE`), then check the proposal's premises against the current base. The handoff never infers approval: it drops the proposal's envelopes and carries its `gate:plan-intent` and `gate:plan-accept` records under the same names (`[CARRIED_GATE]`). It registers the bundle's work scope (`[SCOPE: ...]`; on a `SPEC_SCOPE_REGISTER_FAILED` warning run its `[FIX]`). The base keeps the proposal until the merge.
- `session` depth bound for a PR: `devkit worktree start dev-<slug>` and the printed `cd`; no bundle.
- `spec` depth (inline Planning): `devkit worktree start dev-<slug>`, run the printed `cd`, then `devkit spec new <slug>` (`--workflow sdd-spec-bugfix` for a defect), which creates and binds `specs/<YYYY-MM>/<YYYYMMDD>-<slug>/`, then `devkit spec scope register --spec <dir>`, record `plan-intent` and commit: that state is Development's input.
- Guards: `start` inside a linked worktree stops with `WORKTREE_NESTED`. The branch's path taken by another branch, holding uncommitted changes or deleted without `git worktree prune` is `WORKTREE_CONFLICT`; an existing branch, local or on a remote, is `WORKTREE_BRANCH_EXISTS`: continue it ([branches](branches.md) §3) or choose another slug. None of these change anything. A clean worktree already on the branch is reused (`created=no`).

## 2. Work (in the worktree)

- Run the stages as usual (`spec-specify`, `spec-plan`, `spec-tasks`, build, `spec-review`, `spec-sync`), checking each stage boundary with `devkit workflow next --unit <dir>`. `spec-tasks` and `spec-sync` run `devkit spec scope update --spec <dir>`; `devkit spec scope query` shows the other tasks' overlaps. `overlaps=` above 0 informs scheduling and integration order, never a block.
- Commits happen on `<branch>` in this worktree (`git commit`; the commit gate runs there). Commit at every stage boundary; nothing is pushed or merged before `dev-integration`.

## 3. Integrate and finish (after `dev-integration`, in `<base>`)

- `devkit worktree finish` runs devkit-spec's post-finish extension in the base: it removes the finished worktree's scope record and the empty proposal directories a merged handoff left, each reported as a `[NOTICE]` (`POST_FINISH_NOTICE`). A cleanup that fails arrives as its own warning with a `[FIX]`, and the other cleanup still runs: a failed record removal as `SPEC_SCOPE_TIMEOUT`, `SPEC_CONFIG_INVALID` or another registry code (`[FIX]` ends with `devkit spec scope sweep --apply`), a failed prune as `SPEC_PROPOSAL_CLEANUP_FAILED` (`[FIX]`: `devkit spec proposal prune <slug>`, the slug without its prefix); run the `[FIX]` in the base once its cause is resolved. Only an unexpected failure of the extension is `POST_FINISH_EXTENSION_FAILED`: then run both commands by hand. A refused finish runs no extension, so the task stays registered. `devkit spec scope release -w <worktree path>` withdraws a task that is abandoned instead.
- A conflict in `.devkit/installation.json` when integrating the base (two tasks re-synced bundle assets): keep either side, run `devkit sync`, stage the receipt it writes.
- Local merge (`pull_request=auto`, no PR): `devkit worktree finish <branch> --merge`. It refuses a branch whose units hold an unresolved problem or an unanswered question (`WORKTREE_BLOCKED`, one reason per detail; [worker records](worker-records.md)) or that its guard could not verify (`WORKTREE_GUARD_FAILED`). It fetches the base branch's upstream, fast-forwards the base onto `<branch>`, pushes the base branch to its upstream (never forced), removes the worktree and deletes the branch when `delete_branch=yes`. The `[WORKTREE_FINISHED: ... push=...]` field says what happened to the push: `pushed`; `no-upstream` (the base branch tracks no remote; nothing was pushed, say so in the report); `rejected` (`WORKTREE_PUSH_REJECTED`: the upstream moved on; its `[FIX]` integrates it, then pushes); or `failed` (`WORKTREE_PUSH_FAILED`, whose `[FIX]` is the push to rerun once the cause, such as auth, network or a refused update, is resolved with the user). The cleanup finishes either way. Then run `devkit rules check --ci --base <merge-base>` on the result and declare the runner checks yourself, since no CI runner exists without a PR: `devkit workflow next --unit <dir> --given dev-integration --given lint-ci-clean --given merged`.
- Through a PR (`pull_request=required`, or chosen under `auto`): push `<branch>`, open the PR and let it merge only while `devkit workflow envelope check --unit <dir> --format json` on its head reports `"blocked": false` and no `pending_questions`; after the merge is confirmed run `devkit worktree finish <branch>` (no `--merge`; `--merge` is refused with `WORKTREE_PR_POLICY`). The merge test is an ancestor test, so a PR merged by squash or rebase stays `WORKTREE_UNMERGED`: remove that worktree and branch only with the user's authorization.
- Each refusal names its cause and leaves earlier steps done, so the same command resumes once it is resolved: `WORKTREE_BASE_DIRTY` (commit or stash in the base), `WORKTREE_BASE_DETACHED` (check out the base branch), `WORKTREE_BASE_BEHIND` (`git pull --ff-only` in the base), `WORKTREE_MERGE_NOT_FF` (integrate the base into the branch first, `spec-integrate` Step 1), `WORKTREE_UNMERGED` (merge first), `WORKTREE_BRANCH_UNPUSHED` (push the branch to its upstream), `WORKTREE_DIRTY` (commit or discard in the worktree; nothing is ever removed by force), `WORKTREE_LOCKED` (unlock only once the user agrees). `WORKTREE_RUN_FROM_BASE` means `cd <base>` first. `WORKTREE_NOT_FOUND` for a merged branch without the `branch.<branch>.devkitWorktree` marker means devkit did not create it: delete it (`git branch -d <branch>`) only with the user's agreement. A refusal after a change still prints the partial `[WORKTREE_FINISHED: ...]` line.
